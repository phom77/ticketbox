# Design

## Context

The web app uses React and Vite, with separate Axios instances for public and authenticated reads. Both send `vi`. Services already localize HTTP message text from `Accept-Language`. Catalog stores one title and description per concert, caches public list and detail data in Redis and uses the same detail model for the existing organizer preview. Catalog owns the concert write transaction and organization access checks.

## Goals / Non-Goals

- Resolve the language once at the web application boundary and let each feature translate its interface from that selection. Keep concert translations in the Catalog ownership and transaction boundary.
- This release covers web presentation and concert titles and descriptions. Preference persistence is per browser. Email, generated PDF and CSV content, stored notifications, historical order and ticket snapshots, and mobile apps belong to separate releases.

## Decisions

1. **One web language selection.** Initialize from a supported saved preference, then the first matching browser language, then `vi`. Normalize browser region variants to supported language tags. Store explicit choices in browser storage and support an in-memory selection if storage is unavailable. Update the document language and keep the existing router and providers mounted. Reuse one keyboard-accessible selector in public, authentication, buyer and operations layouts, including booking screens and narrow widths. Profile sync would add a service contract and browser/account precedence. Browser persistence covers this release.
2. **Feature message resources.** Use `i18next` and `react-i18next` with a supported-language registry, feature namespaces, English as the source fallback, and native `Intl` formatting. Use whole-message interpolation and locale plural rules. Include labels, status labels, accessibility text, validation and feedback. Preserve raw business data and payment currency, and keep existing business time zones. Feature catalogs and standard plural rules cover the use cases that otherwise require a custom translation layer.
3. **Keep the HTTP and service boundaries.** Set `Accept-Language` from the active selection at request time on both web Axios instances and other browser entry points that display localizable HTTP feedback. Keep machine-readable codes and enums, events, logs, payment protocols and default locale configuration for existing callers. Respect `Vary: Accept-Language` for localized HTTP text. Translate client fallback text and associate rendered HTTP text with the request language. Discard or replace stale-language feedback when a request completes after a switch while applying the business result normally. Keep read retries distinct from mutation execution.
4. **Store authored values by language in Catalog.** Add a locale-keyed collection of title and description values with a new Flyway migration and external ORM mapping. Persist it with the existing concert update and row lock. Keep existing `title` and `description` as compatibility fields. Preserve existing unlabelled content as the original and make it available in the editor without guessing its language. If a concert already has a language-keyed representation, track the unlabelled original independently of the compatibility projection so removing a translation cannot revive the removed text through fallback. For newly authored localized content, derive the compatibility fields deterministically from the available values in a fixed order independent of the UI language. Prefer an authored original when present, then `vi`, then `en` for the compatibility projection. Existing requests that omit localized content still update the original as before and preserve translations. A translation-aware save can explicitly clear one or more fields while retaining a valid title. Reject unsupported tags and invalid values before committing any write.
5. **Select concert copy at render time.** Add authored language variants to the existing public summary/detail and management responses, retaining their existing fields and permissions. The browser selects the requested value, then an available alternate or original per field. A language switch can update cards, details, checkout and organizer preview from the data already loaded. Keep Catalog Redis entries language-independent and use the existing after-commit invalidation for edits. Existing cached entries without variants continue to render their original fields. A per-locale HTTP concert representation would require a locale-specific cache key and a refetch on each switch.
6. **Use the existing event forms.** Share the title/description input behavior between the current create/edit form and the workspace editor. Provide explicitly labelled Vietnamese and English inputs, explain the one-title rule, preserve unsaved values when the display language changes, and display empty inputs for missing translations. Preserve existing publication readiness and authorization rules.

## Risks / Trade-offs

- Old Catalog consumers and Redis entries may only supply the compatibility fields. Treat missing translation data as original content and verify current cache and contract behavior after an upgrade.
- The forms and public APIs currently share concert models. Keep management reads and preview behind their existing access checks, test translation-only writes under the same lock, and verify that cache invalidation happens only after commit.
- An English source key may exist without a matching Vietnamese entry, or a placeholder may drift. Check required keys, placeholders and locale-specific plural forms in CI. Review the existing labels used by assistive technology and test controls with longer copy.
- Historical purchase records and authored venue, artist and ticket-type names can appear alongside translated interface copy. Treat those values as stored content and describe the release scope accordingly.

## Migration Plan

Deploy the Catalog migration and additive API before the web UI. Existing rows retain their original text without language inference or a mandatory backfill. Existing API requests and web builds continue to work. When reverting the web release, keep the additive Catalog migration so authored translations remain available for redeployment.
